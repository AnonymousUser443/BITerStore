## 2. 优先修复的问题

### C01：商品编辑后的文本复审可被绕过

**位置：** [listings.service.ts](../server/src/modules/listings/listings.service.ts)，第 8–9、135–151、162–188 行。

编辑已经上架的商品时，`update()` 会将其改成 `PENDING_REVIEW`，清空 `moderationDecision`，但保留图片的 `APPROVED` 状态。与此同时，状态机允许 `PENDING_REVIEW → OFF_SHELF → ACTIVE`，重新上架只检查必需图片及图片审核状态，不检查当前文本版本是否审核通过。

**复现顺序：** 使用有已审核封面和 ISBN 页的在售商品，修改标题或描述，再依次请求下架、上架，每次携带正确的递增版本号。本地结果为：

```text
编辑后：PENDING_REVIEW
下架再上架后：ACTIVE
moderationDecision：null
```

**影响：** 卖家可以让修改后未经复审的文本重新进入公开列表。单纯禁止 `PENDING_REVIEW → ACTIVE` 不足以封闭这条路径。

**建议：** 记录审核通过的内容版本；只有当前内容与已审核版本一致时才允许卖家直接重新上架，否则进入审核。不要把“图片已通过审核”当作“整个商品已通过审核”。

**验收：** 编辑标题、描述等字段后，无论经过何种允许的状态转换，都不能在管理员复审前公开；未经编辑的正常下架、再上架仍符合产品规则。

### C02：R2 上传校验存在文件替换窗口

**位置：** [uploads.controller.ts](../server/src/modules/uploads/uploads.controller.ts)，第 59–61、82–116 行。

`complete()` 先读取 `pending/` 对象并校验字节，再通过 `CopyObjectCommand` 从同一对象键复制到 `media/`。复制没有绑定刚才读取的对象 ETag 或版本，也没有直接保存已校验的那份字节。

预签名 PUT 的有效期为 600 秒；R2 预签名地址在过期前可以重复使用。因此，在读取和复制之间覆盖源对象，会造成校验对象与最终保存对象不同。[Cloudflare R2 官方说明](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)

**本地复现：** 模拟 S3 在返回合法 PNG 的读取结果后，将源对象替换为相同长度的非图片字节。真实控制器仍返回上传完成，最终对象再次执行 `inspectImage()` 时失败。此复现没有访问或写入生产 R2。

**影响：** 文件魔数、尺寸等校验不能保证最终存储内容有效，数据库记录的 MIME、尺寸也可能与对象不符。此结论不等于图片已绕过管理员审核，也不代表发现了代码执行漏洞。

**建议：** 优先将校验通过的字节直接写入最终对象；或使用读取时获得的 ETag 对复制执行条件约束，并在条件失败时拒绝完成。最终对象应由服务端控制，完成操作还应具备并发与重试保护。

**验收：** 在上传完成的读取、校验、复制各阶段注入同键覆盖和重复完成请求，最终对象必须与通过校验的字节一致，或整个完成操作明确失败。

### C03：恢复演练脚本在解密阶段被已有临时文件阻断

**位置：** [restore-drill.sh](../deploy/backup/restore-drill.sh)，第 23–26 行。

脚本先用 `mktemp` 创建空文件，再执行 `gpg --batch ... --output "$plain_file" --decrypt ...`，但没有 `--yes`。在没有其他覆盖配置的情况下，GPG 批处理模式不会确认覆盖这个已经存在的文件，脚本在 `set -e` 下退出，无法继续执行 `pg_restore`。

**本地验证：** 使用 GnuPG 2.4.5、虚构内容和测试口令生成加密文件；解密到预先创建的空文件时退出码为 **2**，输出长度仍为 0；加入 `--yes` 后退出码为 **0**，恢复内容与原文件哈希一致。未使用生产备份或生产口令，也未执行真实数据库恢复。[GPG 选项说明](https://www.gnupg.org/documentation/manuals/gnupg/GPG-Configuration-Options.html)

**影响：** 交接材料中的恢复脚本目前不能作为可直接执行的灾备工具；“备份可解密校验”与“该恢复脚本可完成恢复”是两个不同验收项。

**建议：** 对脚本自行创建并控制的临时文件明确允许覆盖，保持临时文件权限和退出清理机制；然后在隔离容器与一次性数据库中完成整个脚本的演练。

**验收：** 从加密归档恢复到空白临时数据库，核对迁移记录、关键表数量及图片引用，并记录恢复耗时。不能只验收 `pg_restore --list`。

### C04：默认公开昵称包含完整学号

**位置：** [identity.service.ts](../server/src/modules/identity/identity.service.ts)，第 66、96–100 行；[listings.service.ts](../server/src/modules/listings/listings.service.ts)，第 37–40 行。

校园认证为新账号生成的昵称是 `BITer${studentNumber}`；账号恢复和部分旧默认昵称更新也采用这一规则。公开商品接口虽然没有直接返回 `studentNumber` 字段，但会返回卖家的完整 `nickname`。

**触发条件：** 新用户保留系统默认昵称，发布商品并通过审核。此时游客可以从公开卖家昵称中读出完整学号，无需登录。

**证据边界：** 当前公开列表只返回 1 条商品，其卖家昵称没有匹配该默认格式。本次确认的是默认数据生成与公开输出之间的泄露路径，没有确认当前公开样本已经发生泄露，也没有将真实学号写入报告。

**建议：** 默认昵称改为与校园身份无关的随机公开别名；评估已经生成的默认昵称并制定替换策略，避免覆盖用户自行设置的昵称。

**验收：** 新注册及恢复账号的默认公开昵称不包含完整学号；公开商品、聊天成员和其他展示资料不会因系统默认值暴露身份编号。

## 3. 功能与稳定性问题

### C05：聊天详情隐含“前 50 个会话”限制

**位置：** [H5 api-repository.ts](../web/app/lib/api-repository.ts)，第 245–251 行；[小程序 api-repository.ts](../miniProgram/src/domain/api-repository.ts)，第 65 行。

两个客户端的 `getThread(id)` 都读取目标会话消息，同时读取 `/conversations?limit=50`，然后只在这 50 条摘要中寻找目标。H5 找不到就返回 `null`，小程序则抛出“会话不存在”；均没有继续使用 `nextCursor`。

**影响与复现：** 用户有超过 50 个会话时，列表分页能展示的旧会话，进入详情后却可能加载失败。即使消息接口已经成功返回数据，详情仍会失败。本地执行真实 H5 仓库方法，在返回有更多页的 50 条摘要时已复现返回 `null`。

**建议：** 增加带成员鉴权的单会话摘要接口，让详情按 ID 查询；短期可正确遍历分页，但不宜让每次轮询都读取大量无关摘要。

**验收：** 至少准备 51 个会话，验证从列表、直达链接和冷启动均能打开最旧会话；无权访问的会话继续被拒绝。

### C06：自己的非在售商品没有完整的图片读取路径

**位置：** [listings.service.ts](../server/src/modules/listings/listings.service.ts)，第 12–40、83–101 行；[media.controller.ts](../server/src/modules/uploads/media.controller.ts)，第 19–38 行。

`getMine()` 已能返回卖家的非公开商品，但仍使用公开商品的图片过滤器和 `/api/v1/media/:id` URL。该图片接口只允许 `ACTIVE` 商品；另一条 `/media/review/:id` 路径又要求管理员权限。

**影响：** 已下架或已售商品仍可能返回图片 URL，但实际取图会得到 404；待审核图片在 owner 查询时就被过滤掉。缓存可能短暂掩盖问题，冷启动或缓存失效后更明显。历史聊天中的非在售商品卡片也存在同类取图限制。

**建议：** 区分公开媒体、卖家本人媒体和管理员审核媒体权限，提供经过所有权鉴权的私有读取路径。聊天是否保留交易图片需明确产品规则并单独限制会话成员访问，不能放宽现有公开接口来解决。

**验收：** 卖家可查看自己的待审、下架、已售商品所需图片；其他用户不能借此读取私图；ISBN 页仍不进入公开响应。当前结论来自代码链路检查，本轮未修改真实商品状态做线上复现。

### C07：并发已读请求会使已读位置倒退

**位置：** [conversations.service.ts](../server/src/modules/conversations/conversations.service.ts)，第 97–105 行。

`read()` 先读取 `lastReadMessageId`，在 JavaScript 中比较，然后执行无游标条件的 `update()`。两个请求可能同时看到旧值：较新的消息 ID 先写入，较旧的请求随后覆盖它。

**本地复现：** 两个请求分别标记消息 `10`、`20` 已读，控制 `20` 先落库、`10` 后落库，最终游标变成 `10`。

**影响：** 多标签页、多设备或网络延迟可能使已经阅读的消息重新计入未读。现有单次请求中的大小比较不能保证并发单调性。

**建议与验收：** 在数据库更新条件中加入“当前游标为空或小于目标 ID”，或采用原子取最大值。并发及乱序提交后，最终游标必须始终等于已确认的最大 ID，并保留消息所属会话校验。

### C08：禁言状态实际会升级为无法维持登录

**位置：** [auth.service.ts](../server/src/modules/auth/auth.service.ts)，第 190–192、212–219 行；[auth.ts](../server/src/common/auth.ts)，`AuthGuard`、`CampusVerifiedGuard`、`NotMutedGuard`。

现有权限设计允许 `MUTED` 用户读取个人数据和会话，只禁止互动写操作；但 `issue()` 拒绝所有非 `ACTIVE` 用户，`refresh()` 也只接受 `ACTIVE`。

**本地复现：** 对已认证的 `MUTED` 用户，校园登录返回 **403**，有效刷新凭证也返回 **401**。既有访问令牌未过期时可能仍可读取，过期后则无法继续维持登录。

**影响：** 禁言表现随访问令牌是否过期发生变化，与“保留读取、禁止互动”的边界不一致；现有禁言测试主要检查写操作拦截，没有覆盖重新登录和刷新。

**建议与验收：** 统一禁言语义。如果维持当前产品定义，允许禁言用户建立和刷新受限会话，写操作继续由服务端阻止；分别验证禁言前后、令牌过期、重新登录以及解除禁言。

### C09：Server 的标准启动命令指向错误产物

**位置：** [server/package.json](../server/package.json)，第 9 行；[tsconfig.json](../server/tsconfig.json)，第 6、15 行；[Dockerfile](../server/Dockerfile)，末行。

`npm run build` 实际生成 `dist/src/main.js`，而 `npm start` 执行 `node dist/main.js`。

**实际验证：** 构建成功，随后 `npm start` 报 `MODULE_NOT_FOUND`，退出码为 1。

**影响：** 按标准 npm 流程启动服务失败，影响接手开发和非 Docker 运维。当前生产 Dockerfile 使用正确的 `dist/src/main.js`，因此本项不能解释为生产 API 已不可用。

**建议与验收：** 将启动脚本与构建输出统一；在配置好隔离数据库和 Redis 的环境中补做“构建→标准启动→健康检查”验证。
