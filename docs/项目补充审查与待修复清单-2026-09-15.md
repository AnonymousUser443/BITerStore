## 1. 结论摘要

项目现有自动化测试和基础构建质量较好，但本轮补充审查发现，仍有若干安全能力和产品行为没有形成真正闭环。建议在扩大真实用户范围前，优先处理以下事项：

1. 让 H5 游客读取真实公开商品，同时为公开读取接口补齐缓存、限流、查询约束和监控。
2. 收窄公网 BIT-Login 路由，并修复 Cookie 会话降级和退出登录不彻底的问题。
3. 在服务端真正执行拉黑关系和图片审核状态，不能只保存数据库标记。
4. 修复聊天未读、通知、历史分页、上传孤儿对象和商品分页筛选问题。
5. 补齐依赖升级、容器网络隔离、健康检查、备份恢复和真机验收。

关于“游客真实浏览是否会耗尽数据库流量”的决定如下：

> **允许游客查看真实商品，但必须与公开读接口抗刷措施同批上线。保留演示商品不能作为数据库保护措施。**

原因是 `GET /api/v1/listings` 和 `GET /api/v1/listings/:id` 当前已经是匿名公开接口。即使 H5 游客继续显示本地演示数据，恶意请求者仍可跳过页面直接调用 API。切换真实数据主要增加的是正常用户流量，而不是新建一个原本不存在的攻击入口。

## 2. 游客真实商品与数据库流量风险

### 2.1 当前实现

- 公开列表控制器没有认证 Guard：`server/src/modules/listings/listings.controller.ts:8`。
- 公开详情同样无需登录：`server/src/modules/listings/listings.controller.ts:12`。
- 每次列表请求都会直接执行 Prisma/PostgreSQL 查询，没有 API 缓存：`server/src/modules/listings/listings.service.ts:22-32`。
- 单次请求数量已限制在 1–50 条，但搜索词长度、过滤枚举和请求频率没有统一约束。
- Nginx 的 `/api/` 路由当前没有 `proxy_cache` 或 `limit_req`；只有 `/media/` 设置了客户端缓存头：`deploy/nginx.conf:62-88`。
- H5 只有登录用户才使用真实 API；游客走本地种子仓储：`web/app/lib/repository.ts:174-180`。

### 2.2 风险判断

恶意重复请求确实可能带来以下消耗：

- 重复列表和详情查询增加 PostgreSQL QPS、连接占用和网络流量。
- 不断改变 `q`、`cursor`、`campus` 等参数可以制造大量不同查询，绕过简单 URL 缓存。
- 当前搜索对标题、作者、ISBN、课程四列执行不区分大小写的包含匹配；数据增大后，随机搜索词可能造成高成本扫描。
- 批量抓取商品详情和图片会同时消耗 API、数据库、对象存储和公网出站流量。
- 校园网/NAT 下可能有大量正常用户共享一个公网 IP，因此仅做严格的单 IP 限流也可能误伤。

风险是可控的。正确方案不是强制游客登录，而是让公开内容通过缓存承接绝大多数重复读取，并在边缘层和应用层共同限制异常流量。

### 2.3 建议防护方案

#### 第一层：边缘与 Nginx

- 在可信代理链上取得真实客户端 IP；只信任明确的 Cloudflare/NPM/内层 Nginx 地址或固定代理跳数，不能继续无条件 `trustProxy: true`。
- 对公开列表、搜索、详情分别设置限流区，返回标准 `429` 和 `Retry-After`。
- 初始建议值只作为压测起点：
  - 无搜索列表：每 IP 60 次/分钟，允许约 20 次短时突发。
  - 搜索请求：每 IP 30 次/分钟，允许约 10 次短时突发。
  - 商品详情：每 IP 120 次/分钟，允许约 30 次短时突发。
- Cloudflare 层增加按路径的速率规则、Bot/异常流量规则和紧急封禁开关。
- 不能只依赖单 IP：应用层还应结合匿名设备标识、已登录用户 ID、请求路径和全站总速率。匿名标识只能作为辅助维度，不能视为可信身份。

#### 第二层：公开响应缓存

- 无搜索的首页列表优先使用 Nginx/CDN 或 Redis 缓存，建议 TTL 15–30 秒，并允许短时间 `stale-while-revalidate`。
- 商品详情建议缓存 30–60 秒；商品下架、封禁、删除或审核拒绝时主动失效对应缓存。
- 搜索结果只缓存经过规范化且长度受限的参数；使用有容量上限的 LRU/Redis 缓存，避免攻击者用随机搜索词填满缓存。
- 缓存键只包含白名单参数：`q`、`campus`、`category`、`condition`、价格区间、排序、`cursor`、`limit`。未知参数直接拒绝，不能进入缓存键。
- 只缓存公开、与用户无关的 GET 响应；不得缓存包含收藏状态、私聊、个人资料或管理信息的响应。
- 增加 `ETag`/`If-None-Match`，让未变化数据返回 `304`，降低响应流量。
- 对首页第一页可保留最近一次安全快照；数据库短暂不可用时可以返回短期 stale 数据，但被封禁/删除内容必须有主动失效通道。

#### 第三层：应用接口约束

- 使用 Redis 支持的分布式限流，覆盖所有 API 实例；Nginx 限流作为第一道保护。
- 将公开列表默认 `limit` 保持在 20，最大 50；验证 cursor 格式并拒绝无效值。
- 搜索词设置最大长度（建议 50）和合理的最小有效长度；去除首尾空格并统一大小写/Unicode 规范。
- 校区、分类、成色和排序只接受服务端枚举；价格必须是合法非负整数区间。
- 前端搜索增加约 300ms debounce，并取消已经过时的请求。
- 对高成本搜索设置独立配额；必要时只对输入完成后的搜索提交请求。
- 限流服务故障时，公开读取可由 Nginx 的保守限流继续保护；登录、上传、举报等敏感写操作应采用更严格的失败策略。

#### 第四层：数据库与查询

- 为公开列表建立匹配查询顺序的复合索引，例如活动状态、创建时间和 ID；按真实查询量评估校区、分类组合索引。
- 当前四字段 `contains/ILIKE` 搜索在数据增长后应改为 PostgreSQL trigram/全文索引，或独立搜索服务。
- 设置数据库连接池上限、查询超时和慢查询日志，防止单类请求占满全部连接。
- 避免列表响应展开不必要的数据库字段和全部图片内部字段，使用明确的公开 DTO。
- 为数据库 QPS、活动连接、查询 P95/P99、慢查询数和出站流量设置告警。

#### 第五层：容量与异常监控

- 监控每条公开路由的请求速率、`429` 比例、缓存命中率、响应大小和错误率。
- 监控参数基数，尤其是单位时间内不同 `q` 和 cursor 的数量。
- 记录经过脱敏/散列的来源维度，避免在日志中保存校园密码、令牌或完整敏感查询串。
- 预留紧急模式：关闭搜索、降低最大 `limit`、只提供缓存首页、临时启用挑战页面。

### 2.4 游客真实列表的验收标准

1. 游客首页和商品详情来自真实公开 API，不再使用演示种子商品。
2. 收藏、发布、私聊、举报等写操作仍要求登录和对应权限。
3. 在缓存 TTL 内连续请求同一列表 100 次时，数据库查询次数应保持在可解释的极低数量，而不是 100 次。
4. 超过配置阈值的流量稳定返回 `429`，正常页面短时并发不会被误伤。
5. 随机超长搜索词、未知过滤参数和无效 cursor 返回 `400`，不进入数据库高成本查询。
6. 商品下架、封禁或删除后，其列表、详情和媒体缓存能够主动失效；不得长期继续公开。
7. 缓存响应不包含任何账号相关或后台字段。
8. 压测只在本地或隔离测试环境执行，不对生产环境实施破坏性压力测试。

## 3. 本轮补充发现的待修复问题

### 3.1 高优先级

#### H1：H5 游客展示演示商品而非真实商品

证据：`web/app/lib/repository.ts:174-180` 仅在存在非 `guest` 学号时选择 API；`web/app/components/mobile-app.tsx:349` 将游客标记为 `guest`。

影响：游客看不到真实在售商品；真实分享链接在未登录且无缓存时可能显示不存在；H5 与小程序行为不一致。

整改：完成第 2 节的缓存、限流和输入约束后，让所有公开读操作使用真实 API，仅对写操作进行登录拦截。

#### H2：拉黑记录没有在聊天链路执行

证据：`server/src/modules/moderation/moderation.controller.ts:93-111` 只保存/删除 Block；`server/src/modules/conversations/conversations.service.ts` 创建会话、发送、读取时均不查询 Block。

影响：被拉黑者仍可新建会话或继续发送消息，安全功能名义上存在但实际上无效。

整改：在创建会话、发送消息、会话列表/详情入口执行双向拉黑检查；明确已有会话变为不可发送还是完全隐藏；补充客户端拉黑及管理入口。

#### H3：图片审核状态没有形成公开访问边界

证据：`server/prisma/schema.prisma:176` 默认 `PENDING`；项目没有修改该状态的完整流程；`server/src/modules/listings/listings.service.ts:17` 和 `server/src/modules/uploads/media.controller.ts:21` 未按审核状态过滤。

影响：待审核图片可直接出现在公开商品中。生产只读抽样已经复现 `PENDING` 图片公开且媒体返回成功。

整改：保守方案是只有 `APPROVED` 图片能够公开；补充审核队列、后台操作、拒绝原因和缓存失效。若产品决定暂不做内容审核，也应明确记录这一风险，不能把 `PENDING` 字段视作已经存在的安全能力。

#### H4：公网暴露了完整 BIT-Login 服务

证据：`deploy/nginx.conf:44-60` 代理整个 `/bit-login/`。锁定的 BIT-Login 上游提交除认证 challenge 外，还提供成绩、课程、学生数据、下游 Cookie、ICS 和临时文件接口；这些接口可接收原始学号密码或 challenge token。

影响：没有证据表明可以在无凭据情况下读取学生数据，但当前公网攻击面显著超出梨苑儿登录所需范围，可能被用于凭据代理、暴力尝试和资源消耗。

整改：按前端实际调用建立精确路由白名单；拒绝数据、Cookie、文档和临时文件路由；对 `/api/auth/start` 增加 IP/账号/全局并发限流，并确保密码和 challenge token 不进入访问日志。

#### H5：Cookie 会话可被客户端请求降级为 body token

证据：`server/src/modules/auth/auth.controller.ts:46-55` 从 Cookie 取得 refresh token 后，仍信任请求体中的 `sessionTransport`。

影响：一旦出现同源 XSS，脚本可请求 body transport，将本应只存在于 HttpOnly Cookie 的长期 token 导出，扩大 XSS 的持久化影响。

整改：会话传输方式由服务端根据登录流程和 token 来源决定；Cookie refresh 只能继续签发 Cookie，不能被请求体覆盖。认证、刷新和个人数据响应统一增加 `Cache-Control: no-store`。

#### H6：H5 退出登录失败时会显示为已退出

证据：`web/app/components/mobile-app.tsx:610` 在服务端退出失败后仍于 `finally` 清理界面并跳转；浏览器 JavaScript 无法自行清除 HttpOnly Cookie。`web/app/components/mobile-app.tsx:111-117` 也没有删除聊天、通知、收藏和个人商品快照。

影响：刷新页面后可能恢复登录；共享设备上可能残留上一账号的聊天和账号数据。

整改：只有服务端成功清 Cookie/撤销 session 后才确认退出；失败时明确提示并重试，或进入阻止自动恢复的“待退出”状态。所有账号缓存按用户命名并在退出、过期、换号时统一清除。

### 3.2 中优先级

#### M1：聊天未读、实时刷新、历史分页和通知不完整

- 会话列表为每个会话附带最近 50 条消息，且会话本身没有分页：`server/src/modules/conversations/conversations.service.ts:7-22`。
- Redis 未读数会被增加和删除，但列表接口从未读取，客户端把缺失的 `unread` 映射成 0。
- H5 聊天页只加载一次，没有轮询、SSE 或 WebSocket，也没有提交已读。
- 消息历史只支持读取更新消息，没有向前加载旧消息的客户端流程。
- 通知只有查询接口，项目中没有可靠的通知创建和标记已读链路。

整改：会话列表只返回摘要和准确未读数；消息独立双向游标分页；统一数据库中的已读真相；H5 与小程序采用相同的实时/有限轮询策略；补齐通知产生、查询和已读接口。

#### M2：已完成但未关联商品的上传对象不会清理

证据：`server/src/modules/uploads/uploads.controller.ts:33` 只限制未完成 pending 数量；完成后记录具有 `uploadedAt` 且 `listingId` 仍为空。`server/src/maintenance/cleanup-pending-uploads.ts:109-127` 只清理 `uploadedAt: null`。

影响：用户完成上传后放弃发布，或商品创建失败，会永久留下数据库记录和 R2 对象；完成一批后即可继续申请下一批，绕过 pending 数量限制。

整改：为已完成但未绑定的对象设置 TTL 清理；增加用户总文件数/字节数/频率配额；提供取消上传或发布预留机制；商品创建时用事务和条件更新原子绑定图片。

#### M3：同步图片处理和条码识别可能阻塞 API

证据：`server/src/common/image-validation.ts` 在 Node 主线程同步执行图片结构、CRC 和解压检查；`server/src/modules/books/books.service.ts` 使用高强度条码识别。

影响：重复上传特殊图片或高频识别可能占用事件循环和 CPU。

整改：增加上传/识别限流、并发信号量和超时；将高成本处理移入 worker thread/独立任务进程；保持严格的文件、像素和解压输出上限。

#### M4：请求 DTO 和错误边界不严格

证据：没有全局 ValidationPipe；多个控制器使用 `body: any`。`server/src/modules/listings/listings.service.ts:70` 的更新接口可接受空标题、非法价格和任意校区；消息 cursor/read ID 直接执行 `BigInt()`。

影响：非法数据可能进入数据库，或把应为 `400` 的客户端错误变成 `500`；版本字段虽然递增，但更新接口没有真正执行乐观并发检查。

整改：增加白名单 DTO、枚举、长度和数值范围；禁止未知字段；所有 ID/cursor 在服务层前验证；PATCH 使用期望版本条件更新并在冲突时返回 `409`。

#### M5：商品筛选和分页只覆盖前 50 条

证据：`web/app/lib/api-repository.ts:167-177` 和 `miniProgram/src/domain/api-repository.ts` 只请求最多 50 条，再在客户端执行价格、成色和价格排序；客户端忽略 `nextCursor`。

影响：商品超过 50 条后，筛选可能错误显示为空，价格排序只对第一页有效，“我的发布”也无法继续加载。

整改：服务端实现全部过滤和排序参数；客户端使用 cursor 分页/无限加载；搜索 debounce 和请求取消与第 2 节同时实施。

#### M6：依赖存在待升级安全公告

- 服务端锁定 `fastify@5.11.3`，低于两项高危请求校验问题的修复版本 5.12.2：
  - <https://github.com/fastify/fastify/security/advisories/GHSA-9q9j-q6p8-xq58>
  - <https://github.com/fastify/fastify/security/advisories/GHSA-hwr6-493r-vm6h>
- 当前代码未发现使用公告涉及的特殊 schema，因此不能据此断言生产路由已可利用，但依赖本身应升级并回归。
- `web` 的独立 Next.js 依赖为 16.2.6，处于 2026 年 8 月关键漏洞修复版本之前：<https://nextjs.org/blog/august-2026-security-release>。生产 H5 当前由 Taro 静态构建，不运行 Next 服务端，因此主要影响 Golden Reference 被独立启动或部署的场景。
- MiniProgram 自定义依赖门禁当前通过，但仍依赖审核例外；应按复核日期继续升级 Taro/webpack 工具链，不能把“门禁通过”理解为零漏洞。

### 3.3 其他应改事项

1. `server/src/main.ts:13` 在生产无条件 `trustProxy: true`，应限制可信代理。
2. Redis 没有密码/ACL，所有 Compose 服务处于同一默认网络；应拆分网络并限制可访问服务。
3. `deploy/book-metadata-worker/src/index.js:167` 在未配置 `PROXY_TOKEN` 时会放行；应改为缺少配置即拒绝。生产探测显示当前 token 已配置，但代码仍存在配置回归风险。
4. 健康检查只验证 PostgreSQL，没有覆盖 Redis、R2、BIT-Login 和必要的外部依赖。
5. H5 会注册 `/sw.js`，但生产请求返回 404；应正确复制 service worker，或删除不真实的离线能力声明。
6. Swagger 的全局前缀、Nginx 路由和 CSP 不一致，生产 `/api/v1/docs` 返回 404；应明确关闭生产文档或仅在受控内网正确发布。
7. API 安全响应头由 Nest 和 Nginx 重复发送，应确定唯一责任层。
8. 小程序把未知/空校区映射成“良乡”，可能错误展示交易地点；应统一为“未设置”。
9. 小程序选择图片后统一声明 `image/jpeg`；PNG/WebP 真机文件可能因 MIME 不匹配被服务端拒绝，应检测真实类型。
10. 消息举报只验证消息存在，没有验证举报人属于该会话；应增加成员关系检查。
11. 账号删除会保留学号/身份关联并阻止重新注册；应明确恢复、匿名化和依法保留策略，并向用户准确说明。

### 8.2 游客抗刷与数据库流量结论

游客可以查看真实公开商品，但单纯隐藏真实数据不能保护数据库，因为攻击者可直接调用公开 API。现已形成以下纵深防护：

- 列表、搜索和详情使用参数白名单、严格游标/枚举/长度约束、数据库索引、Redis 短缓存、并发请求合并、ETag，以及应用层和 Nginx 双层限流；随机查询参数不能无限制造有效缓存键。
- 列表、搜索、详情分别使用独立的每 IP 限额，并有全局 API 速率/并发兜底；公开媒体另设每 IP 180 次/分钟和全局 3600 次/分钟保护。
- ISBN 查询改为仅已认证且已验证用户可访问，并设置每 IP 30 次/分钟和全局 2 次/秒限制；登录交换/刷新/注销等入口也有每 IP 与全局限额。
- 图片和商品只有满足审核与状态条件才公开；ISBN 凭证只允许受保护的管理员审核接口读取。
- 这些措施显著降低重复请求直接消耗 PostgreSQL 的风险，但不能替代容量监控和边缘防护。Cloudflare 规则、告警和隔离环境 QPS/缓存命中基线仍是上线扩量前的外部任务；未对生产实施破坏性压力测试。
