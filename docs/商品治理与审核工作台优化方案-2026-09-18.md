# 商品治理与审核工作台优化方案

日期：2026-09-18。依据当前后台、服务端实现及项目交接文档整理。

本文是分阶段实施方案。第一阶段已在当前工作区完成：商品治理拆为 **审核工作台、全部商品、审核记录** 三个固定页签；审核时直接展示完整内容，审核队列严格只收待审核商品；所有商品始终能在“全部商品”中查询当前状态，处理记录能在“审核记录”中追溯。退回修改、准确审核轮次和完整生命周期事件仍属于后续阶段。

## 当前实现状态

- 已完成：严格 `PENDING_REVIEW` 队列、最久等待优先排序、审核／全部／记录三个入口、状态统计、双栏完整审核工作台、受保护封面及 ISBN 凭证、审核完成后的状态结果展示、已售商品不再提供普通审核操作、按商品筛选审核记录。
- 已完成：全部商品区分“当前状态”和“审核结果”；没有历史记录的旧商品明确标记“历史审核记录不完整”，不猜测管理员和时间。
- 待实施：`CHANGES_REQUESTED` 待修改状态、卖家修改并重新提交链路、准确 `reviewSubmittedAt`、审核内容版本快照及完整商品生命周期时间线。

## 1. 当前为什么不好用

| 用户感受 | 当前实现与原因 | 调整方向 |
| --- | --- | --- |
| 每本都要点开详情，审核很慢 | 列表只给小图和摘要；详情与“处置”分别打开弹窗，阅读和决策分离 | 进入工作台即展示第一本待审核商品，详情与操作同屏 |
| 已售、待审核混在一起 | 服务端默认 `reviewState=PENDING` 的条件是“未屏蔽且 `moderationDecision` 为空”，并不是严格的 `status=PENDING_REVIEW`；已售、下架、草稿等历史数据也可能符合 | 审核队列只接收真正待审核的商品，历史治理单独处理 |
| 审完后找不到书和状态 | 操作写入处置标记，商品退出默认筛选。“全部商品／已处置”实际上已存在，但藏在范围下拉框里，难以理解 | 常驻“全部商品”入口，审核完成提示可直接查看该商品 |
| 审过的书缺少后续管理入口 | 前端 `listingActions` 基本只对没有处置标记的商品提供操作，已审核商品通常没有按钮；服务端实际支持更多状态动作 | 依据当前状态与管理员权限展示后续操作，不再用“是否审过”一刀切 |
| 审核拒绝后难以修正 | 当前拒绝映射为 `BLOCKED`，卖家不能编辑被屏蔽商品；资料不清晰也容易被当成违规 | 后续增加独立“退回修改”，与违规屏蔽区分 |
| 不知道谁处理过、为什么、后来发生了什么 | 已有 `ModerationAction`／`AuditLog`，但详情没有完整时间线；这些日志也不等于完整商品生命周期 | 商品详情聚合审核记录；新增状态事件后再补全卖家操作轨迹 |

因此，单纯将表格换成大卡片不能解决状态混杂和审核后不可查的问题，需要同时调整入口、队列条件和处理反馈。

## 2. 页面组织

保留侧栏“商品治理”，进入后展示三个一级页签，不再让管理员组合“商品范围”和“商品状态”来猜当前查的是什么。

| 页签 | 要解决的问题 | 默认内容 |
| --- | --- | --- |
| 审核工作台 | 哪些书需要我现在处理？ | 真正待审核的商品，优先等待最久的记录 |
| 全部商品 | 某本书现在是什么状态？审核通过的书在哪里？ | 全部未删除、已提交商品，含待审核、在售、预订、已售、下架和屏蔽 |
| 审核记录 | 谁在什么时候作了什么决定？ | 按处理时间倒序的审核／治理动作，默认不限操作人 |

首次进入默认打开“审核工作台”，后续记住管理员上次使用的页签和筛选。页签、查询和选中商品使用可恢复的 URL 状态；刷新、浏览器返回及从举报工单跳入后，都能回到原位置。

三个入口始终可见；没有待审核内容时，显示“当前待审核已处理完”，同时提供“查看全部商品”和“查看本次处理记录”。不得显示含糊的“没有数据”，也不自动切换页面。

## 3. 审核工作台：看完直接处理

### 3.1 桌面布局

采用“左侧队列 + 右侧完整审核内容”的双栏布局。右侧将图片、描述和固定操作栏放在同一工作区，避免再开详情弹窗。

```text
商品治理                 [审核工作台 · 12] [全部商品] [审核记录]
待审核 12 本 · 本次已处理 5 本                       [刷新队列]
┌───────────────────┬────────────────────────────────────────┐
│ 搜索待审核商品     │ 大学物理 · ¥10 · 良乡 · 待审核          │
│ 最久等待优先 ▾     │ 卖家昵称 · 提交时间 · 商品编号          │
│                   │                                        │
│ ▣ 大学物理  ¥10   │ [封面大图]       [ISBN 凭证大图]        │
│   等待 35 分钟    │ [其他实拍缩略图，可放大]                │
│ ▣ 高等数学  ¥15   │                                        │
│   等待 28 分钟    │ 书名、作者、ISBN、分类、品相、校区      │
│ ▣ 英语教材  ¥12   │ 完整书籍描述、标签                      │
│   等待 20 分钟    │ 缺失／异常提示 · 相关举报 · 既往处理记录 │
│                   ├────────────────────────────────────────┤
│ 已加载 20 / 36 本 │ [暂跳过] [违规屏蔽] [审核通过并下一本]   │
└───────────────────┴────────────────────────────────────────┘
```

“退回修改”在第二阶段打通卖家修正流程后加入操作栏，不能提前放一个实际执行“违规屏蔽”的同名按钮。图中数字仅为布局示例。

### 3.2 查看体验

- 自动选中第一本，并直接加载完整详情；左侧可随时切换其他商品。
- 封面与 ISBN 凭证并排展示，清楚标注用途；补充实拍紧随其后。图片可放大、缩放及上一张／下一张切换。
- 第一屏突出书名、售价、当前状态和图片；完整描述默认展开。价格、校区、品相、作者、ISBN 等信息集中展示，浏览量等弱相关数据收进次要区域。
- 显示具体问题，例如“缺少 ISBN 凭证”“图片加载失败”，不要用一个空白占位图代替所有异常。允许重试图片。
- 必要详情、封面和 ISBN 凭证未成功加载时，禁用“审核通过”并给出原因；无需强迫每本都打开大图或重复勾选已阅读。
- ISBN 凭证继续通过受保护的审核媒体接口读取，不进入公开商品图片或公共缓存。
- 单条详情加载失败只影响右侧，队列保留；切换商品后不能被上一条迟到的响应覆盖。

### 3.3 连续处理

1. 管理员看完资料，点击“审核通过并下一本”。正常通过无需再弹一次通用“处置”选择框。
2. 提交期间锁定本条操作，按钮显示“正在提交”，防止重复点击。
3. 服务端成功后，该商品退出待审队列，待审核数量同步更新，选中下一本；失败时留在原商品并保留填写内容。
4. 页面显示“《大学物理》审核通过，当前在售 · 查看商品 · 查看记录”。这两个入口不会因为切换下一本消失，可在“本次已处理”中找回。
5. 最后一条处理完显示明确完成态，不误切到其他状态商品，也不返回空白列表。

下一本优先使用当前队列已加载的数据；可预取其详情和小图，但不预下载整个图库。预取失败不阻止当前审核。

“暂跳过”只改变当前管理员本次浏览顺序，不改商品状态，不写“已审核”。显示本次跳过数量，支持回看；所有剩余条目均跳过时提示“还有 N 本暂未处理”，不能报告队列清空。

新提交的商品以“有 N 本新待审核”提示，不自动插到正在阅读的第一条。手动刷新保留当前选中项；当前项已被他人处理时展示结果，再允许切换下一本。

## 4. 全部商品：审完仍然可查、可管

这里保留适合检索、比较的紧凑表格，并提供常驻状态标签：

```text
[全部已提交] [待审核] [在售] [已预订] [已售] [已下架] [已屏蔽]
搜索：书名 / 作者 / ISBN / 卖家 / 商品编号
更多筛选：校区、分类、时间范围、最近处理人、审核结果
```

- 第一阶段使用上述现有状态；第二阶段新增“待修改”。未提交草稿单独入口，不默认混入已提交商品。
- 已删除记录通过单独“回收站”入口查询，默认只读。删除是 `deletedAt` 标记，不能与普通“已下架”混为一谈。
- 页面明确写“全部已提交商品”；从草稿、回收站也可检索到仍保留的数据，避免用“全部”掩盖排除范围。
- 搜索和筛选即时表达当前范围，状态切换清除旧页码；提供“清除筛选”，但不把管理员送回待审默认条件。

建议列：**封面与书名、卖家、价格／校区、当前状态、最近审核结果、更新时间、操作**。完整商品编号可复制；标题过长保留悬停或展开查看能力。

“当前状态”和“审核结果”必须分别展示。例如：

| 商品 | 当前状态 | 审核／治理结果 | 管理员能理解的含义 |
| --- | --- | --- | --- |
| 大学物理 | 已售 | 审核通过 · 张管理员 · 09:20 | 审核通过后卖家售出，不是待审 |
| 高等数学 | 已下架 | 审核通过 · 李管理员 · 昨天 | 当前不售，但以前通过审核 |
| 英语教材 | 待审核 | 当前内容待审；上次通过见历史 | 卖家修改后重新提交，旧结论不代表新内容已获批准 |
| 概率论 | 已屏蔽 | 违规屏蔽 · 原因可查看 | 当前被治理限制 |
| 历史教材 | 在售 | 历史审核记录不完整 | 不能仅因在售就补造“审核通过”记录 |

点击一行打开商品详情侧栏，展示完整内容、当前状态、处理历史和相关举报；关闭后保留筛选、页码及滚动位置。从审核完成提示进入时，即使商品不符合之前的筛选，也应直接定位到详情。

后续操作由“当前状态 + 权限 + 版本”决定。在售／预订可下架或屏蔽；下架／屏蔽的恢复走明确的复核流程；已售默认只读，必要治理单独提供，不能通过一个通用“审核通过”按钮重新变为在售。恢复原状态需要可靠历史依据，没有依据就重新审核。

## 5. 审核记录与商品时间线

审核记录采用事件列表：一条代表一次决定，同一本书多次审核会有多条记录。它与“全部商品一书一行”使用不同统计口径。

每条记录至少展示：书名及编号、动作、处理原因、操作人、处理时间；新记录同时保存处理前后状态、所审核的内容版本。支持按商品、操作人、动作、日期检索，并能打开商品当前详情。

商品详情中的时间线逐步呈现：

```text
09:00  卖家提交审核
09:20  张管理员审核通过：资料完整                 待审核 → 在售
12:30  卖家标记已售                               在售 → 已售
```

以上完整轨迹是目标能力。当前治理日志可以复用，但卖家提交、编辑、预订、售出、下架和删除没有完整统一事件历史；不能仅按 `updatedAt` 猜出动作及操作人。第一阶段先呈现真实存在的审核记录和当前状态，后续对新操作补充生命周期事件，旧数据标注“部分历史未记录”。

“最近处理”不是历史内容快照。若需要查看“当时审的文字／图片”及编辑前后差异，必须保存审核轮次的内容快照和图片引用，并明确媒体保留规则；不得把当前详情伪装成旧版本内容。

## 6. 让拒绝与修正更清楚

推荐第二阶段引入两个明确不同的结果：

| 动作 | 使用场景 | 卖家看到什么 | 下一步 |
| --- | --- | --- | --- |
| 审核通过 | 信息和图片符合要求 | “《书名》审核通过，已上架” | 可交易 |
| 退回修改 | 图片不清、描述不足、ISBN 不对应等可修正问题 | 哪些内容要改、具体原因、“修改并重新提交”入口 | 修改后重新审核 |
| 违规屏蔽 | 确认违规、禁止继续展示 | 违规原因和联系／申诉说明 | 不允许自行编辑绕过屏蔽 |
| 暂跳过 | 暂时拿不准或需核实 | 不发通知 | 留在待审队列 |

退回和屏蔽均要求填写原因，前后端共同校验。提供可编辑的原因模板：“请重新上传清晰 ISBN 页”“图片中的书与填写信息不一致”等，并允许补充说明；正常通过可默认记录“资料审核通过”。

本项目当前未实现独立退回状态。建议新增 `CHANGES_REQUESTED`（界面“待修改”），配合卖家端展示原因、编辑并主动重新提交的能力；编辑保存期间维持待修改，只有明确提交才回到 `PENDING_REVIEW`。需要同步服务端状态机、双端 DTO、页面和测试，不能仅改后台按钮文案，也不能拿卖家主动下架代替退回修改。

通知包含书名、商品编号、结果、原因和下一步入口；再次退回关联对应审核轮次，保留旧原因，不覆盖历史记录。

## 7. 状态与接口如何落地

### 7.1 先修正查询语义

- 待审队列固定条件：`deletedAt = null AND status = PENDING_REVIEW`。发现状态与处置标记异常组合时提示核查，不能偷偷排除真正待审项。
- 全部商品使用独立查询范围，不继承默认 `reviewState=PENDING`。现有接口短期可显式传 `reviewState=ALL`，后续用明确的 `scope` 取代容易互相覆盖的下拉组合。
- 历史无处置标记的在售／已售商品保留原状态，在全部商品中标注记录情况；如需运营复查，设置单独复查入口，不自动塞进首次发布审核队列。
- 商品计数在服务端聚合，不能数当前页。状态数字基于同一搜索／筛选范围，计算各状态时排除已选的状态条件；草稿与删除范围单独统计，审核记录次数不混入商品总数。
- 第一阶段按 `createdAt ASC, id ASC` 稳定排序，并明确这是商品创建顺序。准确的复审等待时间需要新增 `reviewSubmittedAt`；不得把旧商品创建时间当成本次提交时间。

### 7.2 复用与扩展边界

以下路径是建议设计，实施时统一接口命名：

| 能力 | 现有基础 | 建议改动 |
| --- | --- | --- |
| 队列与全量检索 | `GET /admin/listings` | 明确 `scope`、稳定排序、页大小上限；支持商品编号精确查询及校区／分类过滤 |
| 状态计数 | `GET /admin/metrics` 仅有概况 | 增加 `/admin/listing-summary`，返回与筛选条件一致的各状态计数 |
| 完整详情 | `GET /admin/listings/:id` | 复用已有受保护图片；补充当前审核摘要、允许动作与相关举报摘要 |
| 审核／治理提交 | `POST /admin/moderation-actions` | 复用 `version` 乐观锁、事务和请求幂等；收紧动作来源及原因规则 |
| 单书处理记录 | 已有治理表和通用审计接口 | 增加按商品精确过滤、分页的历史接口；避免拉全库日志后前端过滤 |
| 准确复审和生命周期 | 当前只有最新标记及部分日志 | 后续新增提交时间、审核轮次／事件，按需要保存快照 |

扩展新写入记录时，状态修改、审核事件、通知与审计应在同一事务内提交；重复请求不得重复发通知。权限继续由服务端和现有管理员二次验证保证。

### 7.3 多人审核与请求失败

- 提交带查看详情时的 `version`；卖家修改或另一管理员先处理后，旧请求返回冲突，提示“商品已更新，请重新查看”，展示最新状态，不覆盖对方结果。
- 请求超时但结果未知时，使用同一个 `requestId` 和相同提交内容查询／重试；得到明确结果前不能换一个请求编号自动重提，也不能直接进入下一本。管理员修改决定后属于新操作，重新校验版本。
- 后端校验审核通过只作用于允许的状态、内容版本及有效图片；按钮禁用不能替代服务端校验。
- 第一阶段不做长时间占用锁，以免窗口关闭后锁住商品；实际多人并发增加时再加短租约领取与超时释放。
- 不提供虚假的“撤销”：审核通过可能已通知卖家并被买家看到。纠正通过新的、有记录的治理动作完成，不直接删除历史或回滚旧状态。

## 8. 视觉与操作细节

- 延续现有后台配色、字体和组件体系，突出内容阅读和状态区分；不改商品前台视觉基准。
- 大屏双栏；窄屏切换为“队列 → 单条审核”页面，返回保留位置。操作栏固定在可视区域，不能遮住描述或最后一张图片。
- 沿用隐藏侧边滚动条的要求，但保留鼠标、触控和键盘滚动；用内容延续和页码提示可继续浏览，避免多个嵌套滚动区。
- 状态同时使用文字和颜色；审核通过使用主按钮，屏蔽使用危险样式，跳过使用弱按钮。
- 快捷键可后续增加，默认先支持切换和关闭大图；输入原因时不得触发审核快捷键，避免误操作。
- 首期不做“全部一键通过”。批量查看与单本快速审核足以降低操作成本，图片密集内容仍需逐本核对。

## 9. 实施顺序

| 阶段 | 交付内容 | 完成后的体验 |
| --- | --- | --- |
| 第一阶段：优先上线 | 三个固定页签；严格待审条件；双栏直接看详情；通过后下一本；屏蔽原因必填；暂跳过；全部商品状态分类、搜索与计数；现有审核历史；版本冲突和加载失败处理 | 解决现在“反复点开、状态混杂、审完找不到”的主要问题 |
| 第二阶段：修正与追溯 | 退回修改及卖家重新提交；准确审核提交时间和轮次；新操作的完整状态事件；审核通知完善；明确的治理恢复流程 | 可修正问题不必重发商品，处理过程和当前状态可解释 |
| 第三阶段：按实际运营需要 | 内容差异对比、按规则保留历史图片、多人领取、统计等待时长和原因分布、可配置快捷键 | 在审核量增加后提高协作效率 |

第一阶段可尽量复用现有字段和日志，不强行拆分整套商品状态枚举；新增退回状态、准确时间线和历史快照需要迁移及双端适配，单独验收。后台的“审核结果”和“当前状态”先在展示及查询层分开，后续再根据业务规模决定是否拆成独立模型。

## 10. 验收清单

1. 准备待审核、在售、预订、已售、下架、屏蔽、草稿、软删除及历史无处置标记数据；审核队列只包含真正待审核商品。
2. 进入工作台直接看到第一本的完整描述、封面和 ISBN 凭证，无须先点详情；图片失败可重试，不允许误通过。
3. 连续审核 10 本，只需阅读并作决定；通过成功后进入下一本，失败不丢失输入、不提前移除商品。
4. 处理最后一本、跳过全部剩余项、翻页时处理掉最后一条，分别显示正确状态，无空白页和重复审核。
5. 审核通过后能从完成提示和“全部商品”找到该书；卖家标记已售后显示“已售 + 历史审核通过”，不会回到待审队列。
6. 搜索、状态计数和分页来自同一查询范围；审核记录多条不导致商品总数翻倍；刷新／返回保留页面上下文。
7. 两名管理员同时审核，或卖家在审核期间编辑，旧版本操作被拒绝；超时重试不重复生成记录及通知。
8. 已审核商品仍有符合当前状态的治理入口；已售商品不会被普通通过／恢复按钮错误上架，举报结案与商品处置保持各自明确结果。
9. 现有日志真实展示；缺失历史明确标注，不能伪造处理人、时间或内容版本。ISBN 私图不进入游客响应。
10. 第二阶段验证“退回 → 卖家看到原因 → 修改 → 重新提交 → 再次审核”的完整链路，且已屏蔽商品不能通过同一入口绕过限制。
11. 后台单测、类型检查、构建和浏览器交互验收通过；若涉及卖家 H5／微信页面，按项目规则追加双端构建、视觉检查与微信 E2E。
