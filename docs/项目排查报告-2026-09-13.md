## 5. 安全与数据问题

严重级别定义：P0 = 上线阻断或可直接导致账户/权限失守；P1 = 高风险，应尽快修复；P2 = 中风险或需要在正式运营前补齐。以下 P0/P1 条目保留同步前的证据与影响说明，已修复与未复验状态统一见第 6 节。

### P0：生产配置缺失时使用固定默认密钥

证据：

- `server/src/common/auth.ts:6`：`ACCESS_TOKEN_SECRET` 缺失时回退到 `development-only-secret-change-me`。
- `server/src/common/totp.ts:6`：`ADMIN_TOTP_ENCRYPTION_KEY` 缺失时回退到 `development-totp-key`。

影响：生产环境若漏配变量，攻击者可利用已知 JWT 密钥伪造访问令牌；TOTP 加密数据也使用可预测密钥。应在生产启动时强制校验变量存在、长度和随机性，禁止默认值；开发环境可使用显式 `ALLOW_DEV_AUTH`，但不能复用生产路径。

### P1：远程最新提交中的依赖安全门禁当前不通过

证据：

- 远程合并提交 `cda3fa0` 新增 `miniProgram/scripts/audit-dependencies.mjs` 和 `miniProgram/security/npm-audit-policy.json`。
- 实际执行 `npm run audit:dependencies` 得到：未批准 advisory `1193734`、`1193727`；moderate 3 > 2、high 6 > 5、total 12 > 10。

影响：新提交虽然引入了 overrides 和审计门禁，但当前依赖树仍不能通过自身发布门禁；按 `miniProgram/Dockerfile.h5`，生产 H5 镜像构建会在审计步骤失败。应在 Node 22 环境确认 advisory 对应包和修复版本，升级到 Taro 兼容版本或补充经过安全评审的例外，不能直接放宽阈值或使用 `--force`。

### P1：校园身份过期/撤销没有在每次授权时阻断

证据：

- `server/src/modules/identity/identity.service.ts:60,84-86,103` 只保存并返回 `expiresAt`，没有在状态读取或请求授权时拒绝过期身份。
- `server/src/common/auth.ts:28-32` 的 `VerifiedGuard` 只信任 JWT 中的 `campusStatus === 'VERIFIED'`。

影响：校园身份过期或撤销后，已有 access token 仍可发布、聊天、举报等需要认证的操作。应在 Guard/认证服务查询最新 `campusIdentity.expiresAt`、`revokedAt` 和用户状态，或引入可撤销的 token version；过期时同步降级 `campusStatus`。

### P1：公开商品详情和媒体接口未统一限制商品状态

证据：

- `server/src/modules/listings/listings.service.ts:17` 的列表查询在非 `mine` 时限制 `status: ACTIVE`，但 `:20` 的详情查询只有 `deletedAt: null`。
- `server/src/modules/uploads/media.controller.ts:20-22` 只限制图片已上传、已挂载、非 ISBN 和商品未删除，没有限制 `listing.status`。

影响：`DRAFT`、`PENDING_REVIEW`、`BLOCKED`、`OFF_SHELF` 商品可能通过详情 ID 或媒体 URL 继续被公开访问，绕过审核和下架策略。公共接口应只暴露 `ACTIVE`（如需展示 `RESERVED/SOLD`，应明确定义）；所有者和管理员使用受控接口。

### P1：Web 微信登录状态可重复读取令牌

证据：`server/src/modules/auth/auth.service.ts:111-116` 的 `webStatus()` 使用 Redis `GET`；认证成功后 `:146` 将令牌写回同一个 key，但没有一次性消费。

影响：同一个 state 在 60 秒内可多次返回 access/refresh token。state 若经日志、跳转参数、浏览器历史或 Referer 泄漏，可重复建立会话。建议使用原子 `GETDEL` 或 Lua 脚本完成一次性兑换，兑换后立即删除 key，并缩短轮询响应中的敏感数据暴露时间。

### P1：Refresh Token 轮换不是原子操作

证据：`server/src/modules/auth/auth.service.ts:171-177` 先 `findUnique` 校验，再单独 `update revokedAt`，最后创建新 session。

影响：并发请求可同时通过校验并各自生成新 session，扩大 refresh token 重放窗口。应使用带 `revokedAt: null` 条件的原子 `updateMany`/事务，并检查影响行数；失败的并发请求必须返回 401。

### P1：管理员 TOTP 验证缺少失败限流和锁定

证据：`server/src/modules/admin/admin-security.controller.ts:34-46` 的 verify/enable 接口未见 IP、账户级限流、失败计数、冷却或锁定。

影响：6 位 TOTP 可被自动化猜测，且失败行为缺少告警。应按账户和来源 IP 限制频率，连续失败触发指数退避/短时锁定，并记录安全审计事件。

### P1：Taro H5 将 access/refresh token 持久化到可读存储

证据：`miniProgram/src/domain/auth.ts:4-10,13-22,36-46` 调用 `sessionStore.set()`；`miniProgram/src/domain/api.ts:75-95` 通过 `storageAdapter` 持久化完整 `ApiSession`；`miniProgram/src/platform/index.ts:7-28` 使用 Taro 本地存储。

影响：H5 与 Web Golden Reference 的 HttpOnly Cookie 方案不一致，XSS 或恶意脚本可直接读取长期 refresh token。优先让 H5 使用 HttpOnly、Secure、SameSite Cookie transport；若暂时保留 Bearer，至少不持久化 refresh token、缩短有效期并增加 CSP 和 token 轮换。

### P1：注销/换账号没有清理 Taro 草稿、媒体和个人快照

证据：

- `miniProgram/src/domain/api-repository.ts:28-29` 使用全局 `api-draft`；`miniProgram/src/platform/index.ts:136-192` 使用全局 `media` 和 IndexedDB `biterstore-taro-media-v1`。
- `miniProgram/src/domain/auth.ts:46` 注销只调用 `sessionStore.clear()`。
- 其他快照虽然部分按 userId 命名（`api-repository.ts:13-16`），但草稿和媒体没有用户隔离。

影响：同一设备切换账号后可能闪现上一账号的草稿、图片和个人数据，发布流程还可能携带他人图片 ID。应按 userId 命名所有缓存，注销时删除当前用户草稿、媒体、IndexedDB 对象和个人快照；会话过期也要走同一清理路径。

### P1：封禁/撤销后旧 access token 仍可使用

证据：`server/src/common/auth.ts:13-23` 的 `AuthGuard` 只校验 JWT 签名和过期时间，不查询用户 `status`、身份撤销或 token version；管理员撤销主要影响数据库 session/refresh token。

影响：旧 access token 在默认约 15 分钟 TTL 内仍可调用敏感接口。对管理、发布、消息和举报等操作增加实时用户状态校验，或在 JWT 中加入可撤销版本并在服务端缓存/查询。

### P1：注销用户的商品没有同步下架或公共过滤

证据：`server/src/modules/users/users.controller.ts:48` 只撤销 session 并将 User 标为 `DELETED`，没有批量更新该用户商品；商品公共详情也未检查 seller 状态。

影响：已注销用户的商品可能继续出现在详情或历史缓存中，造成交易和隐私问题。注销事务中应将商品统一 `OFF_SHELF`/匿名化，媒体按策略处理；公共查询同时过滤 seller `status = ACTIVE`。

### P2：举报接口缺少目标存在性、重复和频率控制

证据：`server/src/modules/moderation/moderation.controller.ts:8` 只检查 `targetId` 和 `reason` 非空，直接创建 Report。

影响：任意字符串目标均可制造无效举报，重复举报会增加后台和数据库压力。应限定 `targetType` 枚举，验证 listing/user/message 是否存在，按用户/目标做幂等或去重，并增加限流和审核告警。

### P2：上传只校验 MIME 与声明大小，没有校验文件魔数

证据：`server/src/modules/uploads/uploads.controller.ts:21-30,33-40,43-55` 依据客户端 `mime`、`size` 创建上传票据并检查长度；未见图片解码或 magic number 校验。

影响：攻击者可提交伪造 MIME 的文件，异常内容可能进入对象存储或后续处理。服务端应读取文件头并用图片解码器验证真实格式，限制像素尺寸、压缩/重编码，并清理超时的 `pending/` 对象。

### P2：关键接口缺少统一限流

检索 `server/src` 未发现 Nest/Fastify rate-limit 或 Throttler 配置。应重点覆盖校园登录、微信登录和 state 轮询、TOTP verify、ISBN 识别/查询、上传 presign/complete、举报、反馈和消息发送；同时设置请求体、并发和单用户配额。

### P2：后台“禁言”状态尚未落实到业务动作

证据：后台可以把用户状态改为 `MUTED`（`server/src/modules/admin/admin.controller.ts`），但 `AuthGuard` 目前只阻断 `BANNED/DELETED`；消息、发布、举报等接口使用 `AuthGuard/VerifiedGuard`，没有统一的 `MUTED` 行为定义或专门 Guard。

影响：管理员执行“禁言”后，账号仍可能继续发送消息或执行其他写操作，后台展示状态与实际治理效果不一致。应先明确禁言范围（至少消息发送、会话创建/举报等互动动作），再在服务端统一执行并补充恢复/审计测试；不要只在前端隐藏按钮。

### P1：Web 商品详情“举报”按钮原先只显示提示

证据：Web Golden Reference 的商品详情按钮此前只调用 `notify('举报入口已记录')`，没有调用 `/reports`；MiniProgram 同一入口已经提交服务端举报。

影响：同一账号从 H5 举报时不会生成审核工单，造成跨端安全能力不一致。本轮已将 Web 仓储接入 `/reports`，保留登录失效处理，并补充请求回归测试；举报目标存在性、重复和频率控制仍按 P2 待完善。

### P2：H5/API 的安全响应头不统一

证据：`deploy/nginx.conf:48-57` 只在 `/admin/` 配置 CSP、X-Frame-Options、nosniff、Referrer-Policy；公共 H5、`/api/` 和 `/media/` 未统一设置 HSTS、nosniff、frame-ancestors/CSP 等。

影响：公共入口的浏览器防护基线仍不一致。媒体缓存的历史配置还曾使用一年 `immutable`，会放大错误公开资源的影响；本轮已将 `deploy/nginx.conf` 的兼容 `/media/` 路径改为转发到 `/api/v1/media/`，并统一为 5 分钟 `must-revalidate`，但公共 H5、`/api/` 和 HTTPS/HSTS 仍需在网关层补齐。应在确认所有子域名均支持 HTTPS 后添加 HSTS、X-Content-Type-Options、Referrer-Policy 和合适的 CSP/frame-ancestors，并分别评估 API 与媒体缓存。

### P2：下架商品的历史会话仍可能出现失效图片

证据：`server/src/modules/conversations/conversations.service.ts` 会把会话关联商品的图片 URL 返回给参与者；本轮公共 `media/:id` 已限制为 `ACTIVE` 商品和 `ACTIVE` 卖家，因此已下架或注销卖家的历史图片请求会得到 404。

影响：聊天历史仍会保留商品元数据，但图片可能显示为破图，造成界面衔接不完整。应明确“历史会话保留”策略：要么提供仅会话成员可访问的鉴权媒体路由，要么在会话响应中移除不可用图片并由客户端显示已下架占位状态。
