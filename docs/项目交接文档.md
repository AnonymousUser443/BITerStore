## 1. 本轮目标与完成结果

### 1.1 用户提出的四个问题

1. **错误页面处理**：未知前端路由进入站内 404 状态页；直接访问不存在的静态路由时，网关使用相对地址跳转到 `/states?type=404`。旧式 `/books/<id>` 会规范化到 `/books?id=<id>`，不会降级为 HTTP。
2. **会话加载与时间格式**：聊天页等待完整历史后统一去重、按时间升序展示，不再先闪现最新一条再补齐其余消息；会话、通知及详情使用统一的本地化日期时间格式。
3. **高 DPI 背景**：根节点和页面背景覆盖完整视口，已在 `devicePixelRatio=2` 的浏览器环境验证，不再在大 DPI/大视口下露底。
4. **真实商品详情**：修复游客访问时 `/me` 返回 401 导致误跳登录的问题；公开列表和详情现在使用真实公开 API，商品标题、描述和公开媒体可正常显示。动态 ID 会编码，详情统一走规范 query 路由。

### 1.2 游客恶意重复请求与数据库流量

公开商品允许游客浏览是产品要求，但现在不是“每次请求无条件直打数据库”。已建立以下层次：

- 查询参数白名单、类型/范围校验和游标分页，限制高成本或无限结果查询；
- Redis 短缓存及并发请求合并，热门相同请求只触发一次数据库查询；
- ETag/`If-None-Match`，内容未变化时返回 304；
- 应用层和 Nginx 双层限流，公开目录另有专用限流 guard；
- 公开 DTO 仅返回必要字段，ISBN 私图、卖家敏感字段等不进入游客响应；
- PostgreSQL 索引和 trigram 搜索索引降低常见列表/搜索查询成本；
- 日志、健康检查和 request ID 便于定位异常来源。

这些措施显著降低单一游客重复刷新耗尽数据库流量的风险，但不能替代边缘 WAF/Bot 管理、容量告警和隔离压测。Cloudflare 侧规则和告警仍属于外部待办，见第 9 节。

### 1.3 同批完成的安全与使用加固

- 登录/session、Cookie、校园认证、微信绑定和管理员 TOTP 边界继续由服务端强制校验；生产保持 `ALLOW_DEV_AUTH=false`。

- 上传增加配额、文件魔数/结构/尺寸校验、异步图像处理、pending 清理和私有媒体访问控制。
- 账号注销与恢复链接清理、商品状态收敛、举报/治理和审计 request ID 已补强。
- PostgreSQL、Redis、BIT-Login、API 与备份容器使用健康门禁；Redis ACL 和内部网络隔离已启用。
- 数据库备份改为加密输出并增加健康检查、恢复演练脚本及运行手册。

## 3. 一分钟了解项目

梨苑儿是面向北京理工大学校内场景的二手书平台，当前提供：

- H5 与微信小程序双端客户端；
- BIT-Login 校园身份认证，微信作为已认证账号的可选绑定与快捷登录；
- 公开商品浏览/搜索，以及登录后的收藏、发布、聊天、通知和举报；
- 管理与治理后台；
- 封面和 ISBN 页上传、条码识别及书目元数据回填；
- 私有 Cloudflare R2 图片存储和受控媒体读取；
- PostgreSQL、Redis、Nginx、BIT-Login、API、H5、Admin、backup 的 Compose 编排；
- 受限用途的 Cloudflare 书目 Worker。

### 3.1 架构

```text
浏览器 / 微信小程序
        │
        ├── H5 静态资源 ────────────────┐
        ├── /api/v1/* ───────────────┐  │
        └── /bit-login/* ──────────┐ │  │
                                   ▼ ▼  ▼
Cloudflare 隧道 → Nginx → BIT-Login / NestJS API / Taro H5 / Admin
                              │          │
                    PostgreSQL + Redis   ├── 私有 R2 图片
                              │          └── Cloudflare 书目 Worker
                              └── 加密 PostgreSQL 定时备份
```

| 目录 | 技术与职责 |

### 3.2 不可破坏的业务边界

- 游客可浏览、搜索和查看公开商品；收藏、发布、私聊、个人数据及治理操作需要相应身份。
- 发布和修改商品要求 `campusStatus=VERIFIED`，必须由后端 `VerifiedGuard` 强制执行。
- 已认证用户正式发布进入 `PENDING_REVIEW`，管理员审核通过后进入 `ACTIVE`；编辑内容会重新进入审核，治理可将商品置为 `BLOCKED`。重新上架必须仍具有有效内容批准，否则重新提交审核。
- 删除商品是软删除；状态更新使用 `version` 乐观锁；`clientRequestId` 防止重复创建。
- 正式发布必须同时有 `COVER` 和 `ISBN` 图片，最多 6 张；ISBN 页不进入公开接口。
- 生产 R2 Bucket 必须保持私有，对外读取统一经过 `/api/v1/media/:id`。
- H5 列表、详情及用户数据存在本地快照并后台刷新。排查旧数据时应区分客户端快照与 API 响应，不要简单移除缓存。
- 平台当前不提供在线支付、物流、评价、复杂推荐或音视频聊天；新增这些能力前必须重新评估产品、合规与安全边界。

业务数据条数会变化，本文不固化 `ACTIVE`、`SOLD` 等实时数量。

## 7. 数据、备份与恢复

- PostgreSQL 主数据位于 Docker volume `postgres-data`；Redis 不是业务主数据的唯一来源。
- BIT-Login challenge/session SQLite 位于 `bit-login-data`。
- 本机图片模式使用 `api-uploads`；生产图片主要在私有 R2。
- `backup` 容器每天生成 `biterstore-<UTC>.dump.gpg`，使用 OpenPGP AES-256 加密，写入 `deploy/backups/`，默认保留 7 天。

## 8. 回滚原则

当前服务器没有保留旧代码 tar.gz，部署目录也不是版本化 release/symlink 结构。代码回滚必须从已知 Git SHA 重新生成归档。

上一生产版本为 `79560ae`，本次为 API/H5/Admin/backup 保留了 `biterstore-rollback-<component>:79560aebce40` 镜像标签。标签和服务器磁盘不能替代异地备份或长期 release 管理。

回滚前必须：

1. 明确故障版本和目标稳定 SHA；
2. 检查 13 个已应用 migration 与旧代码是否向后兼容；昵称替换属于数据变化，回退镜像不会恢复原值；
3. 如有不可逆数据写入，先制定数据恢复方案，不能只回退代码；
4. 重新制作、校验和部署目标 SHA；
5. 重启 Nginx，执行与正常发布相同的内外网验收；
6. 验收后再更新 `.release-commit`。

Prisma migration 不会自动回滚。不得手工删除迁移记录或为追求“回到旧版本”覆盖生产数据。
