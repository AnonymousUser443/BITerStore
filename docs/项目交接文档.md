## 1. 一分钟了解项目

BITerStore 是面向北京理工大学校内场景的二手书平台。目前已具备：

- H5 与微信小程序双端客户端；
- BIT-Login 校园身份认证，微信作为已认证账号的可选绑定与快捷登录；
- 商品发布、搜索、收藏、上下架、聊天、通知、举报和管理后台；
- 强制上传封面和 ISBN 页，ISBN 条码识别及免费书目元数据回填；
- Cloudflare R2 私有对象存储，图片统一通过受控媒体接口读取；
- PostgreSQL、Redis、Nginx、BIT-Login、API、H5、管理后台和备份容器；
- Cloudflare Worker 书目代理和外部隧道入口。

当前生产环境运行正常。版本 `45365dc` 已完成以下调整：

- 打开 H5 时不再等待会话校验后才渲染整页，会话在后台验证；
- 首页、分类、详情和“我的发布”优先显示本地快照，再后台刷新；
- 发布、改状态和删除后立即更新本地快照；
- 已通过校园认证的用户发布后直接进入 `ACTIVE`，不再进入待审核；
- 部署迁移已把原有已认证用户的待审核商品改为在售。

交接时数据库非删除商品状态汇总为：`ACTIVE=2`、`SOLD=1`，已认证用户的 `PENDING_REVIEW=0`。这是交接时快照，不是长期业务指标。

## 2. 必须遵守的工程规则

开始修改前先阅读仓库根目录的 `AGENTS.md`。最重要的约束是：

1. `web/` 是视觉和行为 Golden Reference，不得为了迁移便利而删除、重命名或重设计。
2. 可见页面修改后，至少运行 `miniProgram` 的 lint、test、H5 build 和 WeApp build。
3. 微信开发者工具服务端口可用时，还要运行仓库内微信 E2E，并检查 route、稳定 E2E 元素、console/exception、结构快照和截图。
4. 平台差异必须封装在 `miniProgram/src/platform/`，页面不能直接散落浏览器或微信专属 API。
5. 禁止提交 `.env`、私钥、CLI token、开发者工具私有配置和真实失败工件。
6. 禁止自动上传微信体验版、提审或发布，也不得修改用户 AppID。
7. 推送、生产部署和其他远程写入操作，每次都必须先得到负责人明确确认。

仓库可能存在未跟踪的 `Assets/generated/`，它属于现有素材工作区。除非任务明确要求，不要删除、覆盖或提交。

## 3. 系统架构

```text
浏览器 / 微信小程序
        │
        ├── H5 静态资源 ────────────────┐
        ├── /api/v1/* ───────────────┐  │
        └── /bit-login/* ──────────┐ │  │
                                   ▼ ▼  ▼
Cloudflare 隧道 → Nginx → BIT-Login / NestJS API / Taro H5 / Admin
                              │          │
                    PostgreSQL + Redis   ├── 私有 R2 图片
                              │          └── Cloudflare 书目 Worker
                              └── 本机定时 pg_dump
```

| 目录/服务 | 技术 | 职责 |
| --- | --- | --- |
| `miniProgram/` | Taro 4.2.1、React 18、TypeScript | 正式双端客户端；构建 H5 和微信小程序 |
| `web/` | React 19、vinext | H5 的 Golden Reference、共享页面组件、CSS 和 H5 Repository |
| `server/` | NestJS 11、Fastify、Prisma | 认证、用户、商品、图片、聊天、治理、书目接口 |
| `admin/` | React 19、Vite | 管理和治理后台 |
| `deploy/` | Docker Compose、Nginx | 生产编排、网关、BIT-Login overlay、备份 |
| `deploy/book-metadata-worker/` | Cloudflare Worker | 受限 ISBN 书目代理，不是通用代理 |
| PostgreSQL | PostgreSQL 17 | 业务主数据 |
| Redis | Redis 7 | 登录轮询状态、书目缓存等临时状态 |
| R2 | Cloudflare R2 | 生产图片对象存储，Bucket 保持私有 |

### H5 与微信端的关系

- H5 生产镜像由 `miniProgram/Dockerfile.h5` 构建。
- 构建时会复制 `web/`，H5 路由直接复用 `web/app/components/mobile-app.tsx` 和 `web/app/globals.css`。
- 微信端使用 `miniProgram/src/pages/` 中的平台页面，并通过 `miniProgram/src/platform/` 处理平台差异。
- 未配置真实 API 时可以运行 DemoRepository；真实登录后由 Repository 切换到 API 实现。

## 4. 核心业务约束

### 4.1 身份与权限

- 游客可以浏览、搜索和查看商品。
- 收藏、发布、私聊及个人数据需要登录。
- 发布和修改商品要求 `campusStatus=VERIFIED`，由后端 `VerifiedGuard` 强制执行。
- 微信不能创建一个独立的未认证正式账号；应先用校园身份登录，再绑定微信。
- 管理接口要求 `MODERATOR`、`ADMIN` 或 `SUPER_ADMIN`，并且管理员 TOTP 已验证。
- 生产环境必须保持 `ALLOW_DEV_AUTH=false`。

### 4.2 商品状态

正常发布路径：

```text
DRAFT ──发布──> ACTIVE ──预订──> RESERVED ──成交──> SOLD
                  │                    │
                  └────下架──> OFF_SHELF <──┘
                                 │
                                 └──重新上架──> ACTIVE
```

- 已认证用户正式发布时直接写入 `ACTIVE`。
- `PENDING_REVIEW` 仍保留在数据库枚举和兼容状态机中，但不再是普通用户发布路径。
- 平台治理仍可使用 `BLOCKED` 阻止违规商品展示。
- 删除采用软删除：写入 `deletedAt` 并把状态改为 `OFF_SHELF`。
- 状态更新使用 `version` 做乐观锁，冲突时提示刷新重试。
- `clientRequestId` 对同一卖家唯一，用于防止重复提交产生重复商品。

### 4.3 图片与 ISBN

- 正式发布必须同时有一张 `COVER` 和一张 `ISBN` 图片。
- 最多关联 6 张图片：封面、ISBN 页和最多 4 张补充实拍图。
- 支持 JPEG、PNG、WebP，单张不超过 5 MB。
- ISBN 页只用于识别和校验，公共商品接口不会返回该图片。
- 生产使用私有 R2；对象先写入 `pending/`，完成校验后移动到 `media/`。
- 对外读取统一走 `/api/v1/media/:id`，不要公开 R2 Bucket。
- 识别优先使用设备条码能力，服务端另有 ZXing WASM 兜底；书目信息由受限 Worker 查询 Google Books、Open Library 和 Crossref。

### 4.4 前端缓存

- H5 使用带筛选条件的商品列表快照和按用户区分的“我的发布”快照。
- 页面先渲染快照，再请求服务器刷新，避免每次进入页面先空白 2–3 秒。
- 发布、状态变更和删除会同步更新快照。
- 登录状态会先根据本地信息渲染，再在后台调用 `/me` 校验。
- 排查“数据没更新”时先区分：界面显示的是旧快照，还是 API 本身返回旧数据。不要简单删除缓存机制来掩盖问题。

## 8. 发布流程

以下为当前发布方式。命令中的 SSH 主机和端口必须从安全渠道取得，不要写入脚本或提交到仓库。

### 8.1 发布前

1. 确认目标提交已经存在，记录短 SHA。
2. 检查 `git status --short`，不要把其他人的未提交改动带入发布包。
3. 根据变更范围运行测试；可见页面变更必须完成双端门禁。
4. 检查 Prisma migration 是否只做可预期、可回滚或可恢复的数据变化。
5. 再次取得负责人对“部署该具体提交”的明确确认。

### 8.2 制作并上传发布包

建议使用 `git archive`，这样不会带入 `.env`、本地依赖、构建产物或未跟踪文件：

```powershell
$Release = "<commit-sha>"
git archive --format=tar.gz --output="biterstore-$Release.tar.gz" $Release
Get-FileHash "biterstore-$Release.tar.gz" -Algorithm SHA256
scp -P <ssh-port> "biterstore-$Release.tar.gz" <ssh-user>@<ssh-host>:/home/<ssh-user>/
```

先在服务器复核 SHA-256，再解压。`deploy/.env`、`deploy/secrets/`、`deploy/backups/` 和 Docker volumes 不在 Git archive 中，正常情况下会保留。

### 8.3 构建和切换

在服务器项目目录执行：

```bash
tar -xzf /home/<ssh-user>/biterstore-<commit-sha>.tar.gz
docker compose -f deploy/config.yaml up -d --build
docker compose -f deploy/config.yaml restart nginx
```

API 容器启动命令会自动运行 `npx prisma migrate deploy`，迁移成功后才启动 NestJS。

`nginx` 重启不能省略：Compose 重建 `h5` 或 `api` 后容器 IP 可能改变，而当前 Nginx 会缓存启动时解析到的上游地址。未重启时首页或接口可能短暂返回 502。

确认所有验收通过后，再更新 `.release-commit` 并删除发布临时包。不要在构建失败时写入成功版本号。

### 8.4 发布后验收

```bash
docker compose -f deploy/config.yaml ps
docker compose -f deploy/config.yaml logs --tail=100 api
curl -fsS http://127.0.0.1:<bind-port>/api/v1/health
curl -fsS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<bind-port>/
```

还必须从公网检查：

- `/` 返回 200，页面能正常渲染；
- `/api/v1/health` 返回 `status=ok`；
- `/api/v1/listings?limit=50` 返回 200；
- HTML 引用的 `js/app.<hash>.js` 是本次构建的新资源；
- 登录、查看列表、进入“我的发布”和发布流程无控制台异常；
- 涉及数据库迁移时，检查 `_prisma_migrations` 和对应业务数据结果。

不要只看 `docker compose up` 的退出码就宣布发布成功。

## 9. 回滚原则

当前部署目录不是原子化 release/symlink 结构，回滚能力有限。发布前应保留上一版本的 Git SHA 和发布包。

代码回滚的一般步骤：

1. 明确导致问题的版本和上一稳定 SHA；
2. 检查新 migration 是否向后兼容；
3. 使用上一稳定 SHA 重新制作并上传 Git archive；
4. 解压并重新执行 `docker compose -f deploy/config.yaml up -d --build`；
5. 重启 `nginx`；
6. 完成与正常发布相同的内外网验收。

Prisma migration 默认不会自动回滚。若新版本已经写入不可逆数据，不得只回退代码；应先制定单独的数据恢复方案。不要手工删除 `_prisma_migrations` 记录。

中长期建议把服务器改造成版本化 release 目录加原子 symlink，并建立自动保留上一版镜像的流程。

### 10.2 常见故障

| 现象 | 优先检查 | 处理方向 |
| --- | --- | --- |
| 首页 502，但 API 正常 | `nginx` 日志是否连接旧 H5 IP | 重启 `nginx`，再检查 H5 容器 |
| API 502/504 | API 容器、迁移日志、PostgreSQL/Redis 健康 | 先读日志，不要反复重建数据库容器 |
| 页面进入时像整页重载 | 是否仍加载旧 JS、Service Worker、登录接口延迟 | 核对资源 hash、浏览器控制台和 `/me` 时延 |
| 列表先空白几秒 | 快照是否写入、筛选 key 是否一致、API 是否失败 | 检查 Repository 快照和后台刷新，不要移除缓存兜底 |
| 发布后仍待审核 | API 是否为旧版本、迁移是否执行 | 检查 `.release-commit`、API 镜像和商品状态 |
| 图片上传失败 | R2 CORS、预签名过期、Content-Type/Length | 核对 Bucket CORS 和上传三步流程 |
| ISBN 有号码但书名不合适 | Worker 数据源顺序、缓存和中文标题选择 | 检查 Worker 响应与 Redis 缓存，必要时清理单个 ISBN 缓存 |
| SSH 偶发断开 | 本地代理链路、连接超时、服务端网络 | 使用较短的幂等命令重试，先确认上一条命令是否已执行 |

## 11. 数据与备份

- PostgreSQL 数据位于 Docker volume `postgres-data`。
- Redis 使用 `redis-data`，它不是业务主数据的唯一来源。
- BIT-Login challenge/session SQLite 位于 `bit-login-data`。
- 本机图片模式使用 `api-uploads`；生产当前使用 R2，但该 volume 仍保留。
- `backup` 容器每天生成一次 PostgreSQL custom-format dump，保存到 `deploy/backups/`，保留 7 天。

重要限制：

- 当前 Compose 中的数据库备份文件没有实际加密，即使环境模板存在 `BACKUP_ENCRYPTION_PASSPHRASE`，编排也尚未使用它。
- 备份仍在同一台服务器，不是异地备份。
- R2 对象、BIT-Login SQLite、密钥和 `.env` 不包含在 PostgreSQL dump 中。
- 尚未在本文交接前完成一次正式的全量恢复演练。

建议最高优先级完成：加密异地备份、R2/SQLite/配置备份清单，以及季度恢复演练。

## 12. 已知问题和后续优先级

### P0：上线前/尽快处理

1. **备份体系**：实现加密异地备份并做真实恢复演练。
2. **Nginx 动态上游**：解决容器重建后缓存旧 IP 的问题，避免依赖人工重启。
3. **R2 生命周期**：当前 S3 凭据缺少 Bucket Settings 权限，`pending/` 1 天清理规则仍需用 Cloudflare 账户 API Token 配置并验证。
4. **微信真机验收**：完成至少一台真机的登录、图片、扫码、发布、聊天和返回栈冒烟。
5. **合规确认**：确认微信主体、服务类目、备案域名、隐私指引及 BIT-Login 自托管许可和维护责任。

### P1：稳定性与可维护性

1. 将手工发布改为版本化、可回滚的自动化流程，但仍保留人工确认门禁。
2. 建立健康监控、错误告警、接口延迟和关键业务指标面板。
3. 为发布、上传、认证、聊天和管理操作补充生产级集成测试。
4. 评估 Taro 官方兼容版本升级，处理锁定依赖树中的上游安全告警；不要使用 `npm audit fix --force`。
5. 拆分约 356–357 KiB 的 H5 入口并建立性能预算。

### P2：产品与数据质量

1. 统计 ISBN 识别和中文书目命中率，再决定是否接入更多中文数据源或本地 OCR。
